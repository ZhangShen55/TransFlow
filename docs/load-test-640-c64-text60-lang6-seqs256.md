# 256 在途序列多语种负载测试报告

## 测试结论

TransFlow 在单 GPU、256 个最大在途序列配置下完成了 64 并发、640 次请求。每个请求固定使用附件前 60 条非空文本，包含 12 种源语言，并翻译为 `zh,en,fr,es,ru,ar` 六种目标语言，共执行 230,400 个翻译单元。

640/640 个请求均返回 HTTP 200。未发生超时、取消、OOM、输出数量或语言顺序错误，测试后 API 与 vLLM 均健康且未重启。vLLM 运行序列峰值为 238，等待峰值为 0，KV Cache 使用率峰值仅为 2.797%。

本配置通过稳定性测试。对于相同短句负载，KV Cache 容量足以继续试验 512 个在途序列；但 GPU 计算已经接近饱和，不能仅凭 KV 余量将 512 直接设为生产默认值。

## KV Cache 与 512 评估

| vLLM 指标 | 峰值 |
|---|---:|
| KV Cache 使用率 | 2.797% |
| 运行序列 | 238 |
| 等待序列 | 0 |
| 采样次数 | 1,038 |

按 312,896 token 的容量估算，峰值时实际占用约 8,752 个 KV token。若序列长度分布保持不变，512 个运行序列预计约占 6% KV Cache，因此本负载下扩大到 512 不会首先受 KV Cache 限制。

GPU 在测试期间多次达到 90% 至 100% 利用率。扩大到 512 更可能增加批次计算时间和单请求延迟，而不一定提高吞吐量。512 候选配置需要同步设置 vLLM `max-num-seqs=512`、应用 `max_inflight_sequences=512`、`batch_workers=16` 和至少 16 个 HTTP 连接，并执行同语料 A/B 压测后再决定是否采用。

## 翻译质量检查

单请求基线生成了 6 x 60 共 360 条译文，六种语言顺序和每组 60 条的数量均正确。自动检查结果如下：

- 空译文为 0，`<unk>` 或 `[UNK]` 为 0。
- 60 条中文译文均包含汉字，60 条俄语译文均包含西里尔字母，60 条阿拉伯语译文均包含阿拉伯字母。
- 英语、法语和西班牙语共 180 条译文中，没有混入汉字、西里尔、阿拉伯、泰、韩、平假名或片假名字符。

人工抽查覆盖上述 12 种源语言到全部 6 种目标语言。模型能够识别混合源语言并保持主要语义，中文和英语整体自然；但并非无误，抽查中发现了少量法语、西班牙语、俄语和阿拉伯语语法问题，以及个别韩语源文翻译时的主语漂移。同语种输入也可能被改写并引入拼写错误。因此当前结果证明语言路由和基本语义有效，不能替代母语人工验收或基于参考译文的 COMET/BLEU 质量评测。

## 工具修正

压测后发现旧 OOM 检测会把成功译文单词中的 `oom` 连续字符误判为 OOM。本次已将检测收紧为仅检查 HTTP 5xx 响应中的完整 `OOM` 或 `out of memory`，并增加回归测试。640 个响应全部为 HTTP 200，容器日志无 OOM，两个容器均保持健康且重启次数为 0，因此本报告记录 OOM 为 0。

机器可读结果见 `docs/reports/load-640-c64-text60-lang6-seqs256.json`。完整 360 条质量抽查输出保留在本机已忽略的 `reports/quality-multilingual-text60-lang6.json`。
