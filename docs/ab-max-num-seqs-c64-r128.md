# max_num_seqs A/B 测试报告

## 结论

在相同的 64 并发、128 请求、60 条多语种文本和 6 个目标语言负载下，依次测试 `max_num_seqs=128/192/256/384/512`。五档均为 128/128 个 HTTP 200，没有超时、取消、OOM、preemption、输出结构错误或容器重启。

`512` 是本次测试范围内的最佳值：输出吞吐 15,712.520 token/秒，P95 请求延迟 46.320 秒。相对 128，输出吞吐提高 77.3%，P95 降低 43.1%；相对 384，输出吞吐仍提高 5.8%，P95 降低 6.3%。KV Cache 峰值仅 5.160%，没有形成容量瓶颈。

本轮在 512 处仍未出现吞吐平台，因此不能将 512 称为全局最优值。由于每档只有 128 个请求，当前项目默认值保持 256；建议先对 512 执行至少 640 请求的持续稳定性验证，再决定是否更新生产默认值。

## 测试方法

每档配置都执行以下独立流程：

1. 重建 vLLM 与 API 容器，清空前一档的 KV、前缀缓存和累计指标。
2. 同步设置 vLLM `max-num-seqs`、API `max_inflight_sequences`、批工作协程数和 HTTP 连接数。
3. 使用相同 60 条文本和 6 个目标语言执行一次不计时预热。
4. 执行 64 并发、128 个请求，并以 0.2 秒采样 GPU、0.5 秒采样 vLLM。
5. 检查 HTTP 结果、输出矩阵、服务健康、OOM、preemption 和容器重启。

| 在途序列 | 批工作协程 | HTTP 连接 |
|---:|---:|---:|
| 128 | 4 | 4 |
| 192 | 6 | 6 |
| 256 | 8 | 8 |
| 384 | 12 | 12 |
| 512 | 16 | 16 |

测试使用用户附件前 60 条文本，源语言覆盖泰语、西班牙语、中文、日语、韩语、俄语、英语、葡萄牙语、法语、阿拉伯语、意大利语和德语。每个请求翻译为 `zh,en,fr,es,ru,ar`，产生 360 个翻译单元；每档共执行 46,080 个翻译单元。

## 分析

从 128 提升到 512 时，输出吞吐持续增长且请求延迟持续下降，说明较大的 Decode 批次可以更充分地摊薄模型权重读取和调度开销。GPU 平均利用率在各档均约为 90%，但该指标无法体现单次迭代承载的有效 token 数；总 token 吞吐从 23,823 提升到 42,238 token/秒，更直接反映批处理效率。

384 和 512 出现少量 vLLM waiting，表示部分内部微批在调度瞬间超过当时可运行容量。由于 waiting 很快被消费，且 preemption、OOM 和超时均为 0，本轮没有表现为故障。512 的峰值 running 为 496，证明配置已被实际利用，而不是只提高了未触达的上限。

KV Cache 使用率随序列数近似线性增长，但 512 的峰值仍只有 5.160%。本工作负载的效率上限来自 GPU 计算与批处理调度，而不是 KV Cache 容量。

## 适用边界

- 每档只有两个 64 并发波次，足以比较明显差异，不足以证明长时间稳定性或精确 P99。
- 每档在独立重启后使用同一组文本预热，前缀缓存命中率均约 83%，保证了 A/B 可比性；随机生产文本的绝对吞吐可能更低。
- 本报告只调整序列数、批工作协程和连接数，没有联合搜索 `max_num_batched_tokens`。
- 测试文本属于短句。更长文本会增加 KV Cache、Prefill 和延迟，最优值可能不同。
- 512 比 384 的边际收益仍为 5.8%，后续可用 640 请求验证 512，也可再测试 640/768 来定位真正平台期。

机器可读数据见 `docs/reports/ab-max-num-seqs-c64-r128.json`。测试结束后运行服务已恢复为项目默认的 256 在途序列、8 个批工作协程和 8 个 HTTP 连接。
