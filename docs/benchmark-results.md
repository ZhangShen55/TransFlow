# 容量测试结果

## 单课程重复短文本基准

此前使用真实课程样本 `test/1节课语音转写.json` 的前 60-80 个片段，并在 64 并发中重复同一请求 payload。该结果适合观察服务在短文本和较高前缀缓存命中率下的基准性能，不代表多课程混合场景。本口径将 335 个片段视为一节完整课程，每个片段翻译为 6 种目标语言（`zh,en,fr,es,ru,ar`）。一次上游请求包含 60-80 个 `text` 元素；64 并发表示同时存在 64 个独立上游请求，不是将 64 个请求合并成一个请求。

在 48GB 显存魔改 RTX 4090D 上，以 vLLM 约 16GB 显存预算、`max_num_seqs=512`、64 并发、持续 600 秒进行真实课程片段测试：

| 每请求文本数 | 请求吞吐 | 335 段课程等效吞吐 | P95 | KV Cache 峰值 | 结果 |
|---:|---:|---:|---:|---:|---|
| 60 | 1.442 请求/秒 | 约 155 节/10 分钟 | 46.3 秒 | 10.6% | 897/897 成功 |
| 70 | 1.205 请求/秒 | 约 151 节/10 分钟 | 54.6 秒 | 10.7% | 768/768 成功 |
| 80 | 1.055 请求/秒 | 约 151 节/10 分钟 | 62.2 秒 | 10.8% | 651/651 成功 |

因此，4090D 在这个“同一课程重复、短文本、高缓存命中率”场景下约为 **900-950 节 335 段课程等效量/小时**。该数字不应用于多课程混合容量承诺；多课程低前缀缓存结果见下文。该数字是片段吞吐折算，不代表单节课程的端到端完成延迟；完整课程需要拆成多个请求。

### 旧基准下的显卡估算

下表只对应上一节的重复课程短文本场景。4090D 数字来自本项目实测；3090 和 4070 Ti Super 是根据该基准作出的独占 GPU估算，必须在目标机器上用相同样本重新压测后才能作为生产承诺。

| 独占 GPU | 335 段课程等效量/小时 | 60 条请求等效量/小时 | 说明 |
|---|---:|---:|---|
| RTX 4090D（48GB 魔改卡） | 约 900-950 节，实测 | 约 5382 请求，实测 | vLLM 预算约 16GB；本次 GPU0 另有约 3.2GB 其他进程，非完全物理空载 |
| RTX 3090（24GB） | 约 430-580 节，估算 | 约 2400-3230 请求，估算 | 显存较充足，但 Ampere 解码吞吐低于 4090D |
| RTX 4070 Ti Super（16GB） | 约 480-620 节，估算 | 约 2700-3500 请求，估算 | 需要单独确认 KV Cache 和 `max_num_seqs`，不应直接套用 512 |

规划时可先采用中间值：4090D 约 920 节/小时、3090 约 500 节/小时、4070 Ti Super 约 550 节/小时。3090 与 4070 Ti Super 的范围有重叠，LLM 解码不能只按游戏算力天梯排序；实际结果受显存带宽、Tensor Core、vLLM 内核和 `max_num_seqs` 共同影响。

4070 Ti Super 只有 16GB 显存，不能直接使用 48GB 显卡的 `gpu_memory_utilization=0.32`。应重新设置显存比例，并对 `max_num_seqs=256/384/512` 独立测试。所有显卡均应使用独占 GPU、相同模型版本、相同课程样本、相同 6 个目标语言和 600 秒持续负载进行最终验收。

详细真实课程报告见 `docs/course-real-load-test-16gb.md`，原始数据见 `docs/reports/course-real-60-c64-600s.json`、`docs/reports/course-real-70-c64-600s.json` 和 `docs/reports/course-real-80-c64-600s.json`。

## 多课程混合低缓存基准

为避免重复发送同一课程造成前缀缓存命中率偏高，使用多课程混合文本构造 64 个互不相同的 payload；每个 payload 包含 60 条文本和 6 个目标语言，共 23,040 个翻译单元。vLLM 重启后清空上一轮前缀缓存，64 个请求一次性并发发送。

| 指标 | 结果 |
|---|---:|
| 64 个请求总耗时 | 98.390 秒 |
| 请求 P50 / P95 / P99 | 97.967 / 98.360 / 98.366 秒 |
| HTTP 200 | 64 / 64 |
| 输入字段 | 3,840 条 |
| 翻译单元 | 23,040 |
| 前缀缓存命中率 | 32.097% |
| KV Cache 峰值 | 13.612% |
| GPU 平均利用率 | 97.040% |
| 等待请求峰值 / 抢占 / OOM | 26 / 0 / 0 |

按本轮实际工作量折算，4090D 约为 39.03 个文本字段/秒、234.17 个翻译单元/秒，即约 **419 节 335 段课程等效量/小时**。98.390 秒是 64 并发满载一轮的保守测量值。

本轮比重复同一课程的结果慢，不能全部归因于前缀缓存：本轮每请求平均 prompt token 约 19,578、completion token 约 19,143，而此前重复短文本测试分别约为 13,662 和 10,892。实际课程文本更长，同时前缀缓存命中率从约 77% 降至 32%，两者共同增加了耗时。

### 低前缀缓存场景的显卡容量规划

以下以本轮 4090D 的 419 节 335 段课程等效量/小时为基准，估算独占 GPU 下的容量。3090 和 4070 Ti Super 仍未在本机实测，不能作为最终生产承诺。

| 独占 GPU | 335 段课程等效量/小时 | 60 条请求等效量/小时 | 类型 |
|---|---:|---:|---|
| RTX 4090D（48GB 魔改卡） | 约 419 节 | 约 2516 请求 | 本项目实测基准 |
| RTX 3090（24GB） | 约 189-252 节 | 约 1134-1510 请求 | 基于实测基准的估算 |
| RTX 4070 Ti Super（16GB） | 约 210-273 节 | 约 1258-1636 请求 | 基于实测基准的估算 |

部署规划建议采用中间值：4090D 约 419 节/小时、3090 约 220 节/小时、4070 Ti Super 约 240 节/小时。两种显卡的估算范围有重叠；LLM 解码吞吐不能只按游戏算力天梯排序，必须在目标卡上用相同的多课程混合样本、64 个不同 payload 和相同 `max_num_seqs` 候选重新压测。

本轮原始报告见 `docs/reports/course-mixed-c64-r64.json`。压测工具通过 `--payloads-file` 支持一组不同请求 payload，可用于后续多课程容量复测。

`max_num_seqs=128/192/256/384/512/640/768/1024` 的同语料 A/B 结果见 `docs/ab-max-num-seqs-c64-r128.md`。在 64 并发、每档 128 请求下，512 的输出吞吐最高，为 15,712.520 token/秒，P95 最低，为 46.320 秒；KV Cache 峰值仅 5.160%。640、768、1024 连续出现吞吐下降和延迟上升，确认 512 是当前负载的效率峰值，项目默认拉起配置已同步调整为 512。

最新的 256 在途序列、64 并发、640 请求多语种负载结果见 `docs/load-test-640-c64-text60-lang6-seqs256.md`，对应机器可读摘要位于 `docs/reports/load-640-c64-text60-lang6-seqs256.json`。先前 128 在途序列的 6,400 请求持续负载结果仍保留在 `docs/load-test-6400-c64-text60-lang6.md`。

最新测试于 2026-09-10 在本机 GPU 0 上完成，使用 Hz-MT2、固定版本的 `vllm/vllm-openai:v0.28.0` 镜像、确定性生成、4096 模型长度和 `gpu_memory_utilization=0.50`。默认配置使用 512 个在途序列，以及由 16 个工作协程执行的 vLLM 批请求，每批最多包含 32 个会话。

## 调度分片对比

每个请求包含 120 个位置、4 条非空多语言字幕样本和 6 个目标语言（`zh,en,fr,es,ru,ar`）。下表每行均为 64 并发测试结果。

| 分片大小 | 吞吐量（请求/秒） | P95（毫秒） | 错误数 | 结构错误数 | OOM |
|---:|---:|---:|---:|---:|---:|
| 8 | 17.663 | 3606.922 | 0 | 0 | 0 |
| 16 | 19.848 | 3203.475 | 0 | 0 | 0 |
| 32 | 19.030 | 3346.668 | 0 | 0 | 0 |
| 60 | 19.728 | 3230.848 | 0 | 0 | 0 |

生产默认值继续使用分片大小 60。该配置在本次 64 并发测试中的吞吐量与最佳值相差约 1%，在较低并发下表现更好，并且可以按预期将 120 个位置拆为两个应用层分片。

## 最大扇出验收

最终验收使用 64 个并发请求，每个请求包含 120 个非空位置和 6 个目标语言，共产生 46,080 个独立模型序列。

| 指标 | 结果 |
|---|---:|
| HTTP 200 成功响应 | 64 / 64 |
| 总耗时 | 92.325 秒 |
| 请求延迟 P95 | 92.300 秒 |
| 翻译单元平均排队时间 | 23.042 秒 |
| 输入 token 数 | 1,428,480 |
| 输出 token 数 | 474,964 |
| 观测到的 GPU 总显存 | 27,788 MiB |
| 超时数 / 取消数 | 0 / 0 |
| 结构错误数 / OOM | 0 / 0 |
| 测试后服务健康 | 是 |

因此，对于本次实测的最大请求结构，600 秒请求超时是保守值。由于翻译长度和其他 GPU 负载会改变延迟，该参数仍保持可配置。

## 被淘汰的调优方案

使用 256 个 HTTP 连接为每个序列单独发送请求时，API 与模型服务均达到饱和，但在 600 秒期限内只完成了部分最大扇出任务。该方案虽未发生 OOM，却产生了超时。最终实现改用 vLLM 原生批量聊天端点，同时仍为每个序列保留独立 future 和结果矩阵坐标。
