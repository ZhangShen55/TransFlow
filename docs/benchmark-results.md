# 容量测试结果

最新的 256 在途序列、64 并发、640 请求多语种负载结果见 `docs/load-test-640-c64-text60-lang6-seqs256.md`，对应机器可读摘要位于 `docs/reports/load-640-c64-text60-lang6-seqs256.json`。先前 128 在途序列的 6,400 请求持续负载结果仍保留在 `docs/load-test-6400-c64-text60-lang6.md`。

最新测试于 2026-09-10 在本机 GPU 0 上完成，使用 Hy-MT2-1.8B、固定版本的 `vllm/vllm-openai:v0.28.0` 镜像、确定性生成、4096 模型长度、`gpu_memory_utilization=0.50`、256 个在途序列，以及由 8 个工作协程执行的 vLLM 批请求，每批最多包含 32 个会话。

## 调度分片对比

每个请求包含 120 个位置、4 条非空多语言字幕样本和 6 个目标语言（`zh,en,fr,es,ru,ar`）。下表每行均为 64 并发测试结果。

| 分片大小 | 吞吐量（请求/秒） | P95（毫秒） | 错误数 | 结构错误数 | OOM |
|---:|---:|---:|---:|---:|---:|
| 8 | 17.663 | 3606.922 | 0 | 0 | 0 |
| 16 | 19.848 | 3203.475 | 0 | 0 | 0 |
| 32 | 19.030 | 3346.668 | 0 | 0 | 0 |
| 60 | 19.728 | 3230.848 | 0 | 0 | 0 |

生产默认值继续使用分片大小 60。该配置在本次 64 并发测试中的吞吐量与最佳值相差约 1%，在较低并发下表现更好，并且可以按预期将 120 个位置拆为两个应用层分片。

## 最大扇出验收

最终验收使用 64 个并发请求，每个请求包含 120 个非空位置和 6 个目标语言，共产生 46,080 个独立模型序列。

| 指标 | 结果 |
|---|---:|
| HTTP 200 成功响应 | 64 / 64 |
| 总耗时 | 92.325 秒 |
| 请求延迟 P95 | 92.300 秒 |
| 翻译单元平均排队时间 | 23.042 秒 |
| 输入 token 数 | 1,428,480 |
| 输出 token 数 | 474,964 |
| 观测到的 GPU 总显存 | 27,788 MiB |
| 超时数 / 取消数 | 0 / 0 |
| 结构错误数 / OOM | 0 / 0 |
| 测试后服务健康 | 是 |

因此，对于本次实测的最大请求结构，600 秒请求超时是保守值。由于翻译长度和其他 GPU 负载会改变延迟，该参数仍保持可配置。

## 被淘汰的调优方案

使用 256 个 HTTP 连接为每个序列单独发送请求时，API 与模型服务均达到饱和，但在 600 秒期限内只完成了部分最大扇出任务。该方案虽未发生 OOM，却产生了超时。最终实现改用 vLLM 原生批量聊天端点，同时仍为每个序列保留独立 future 和结果矩阵坐标。
