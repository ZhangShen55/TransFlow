## 背景

仓库最初只有 OpenSpec 元数据，没有应用代码或依赖。开发环境为全新的 Python 3.12 Conda 环境 `transflow`。本地模型位于 `/var/model_llm/Hy-MT2-1.8B`，部署时通过已忽略的项目目录 `model/Hy-MT2-1.8B` 使用。

现有镜像 `vllm/vllm-openai:v0.28.0`（`sha256:609a5b463503...`）已在本机完成冒烟验证。镜像包含 vLLM 0.28.0、Transformers 5.15.1、带 CUDA 13.0 的 PyTorch 2.13.0，能够识别 `HunYuanDenseV1ForCausalLM`、加载本地模型，并通过 `/v1/chat/completions` 返回正确译文。在 4,096 token 模型长度和 `gpu_memory_utilization=0.5` 配置下，模型加载约占用 3.43 GiB，vLLM 分配约 19.2 GiB KV 缓存。冷启动包含编译过程，耗时超过一分钟。

行为契约见提案及 `translation-api`、`translation-runtime` 增量规格。

## 目标与非目标

**目标：**

- 公开 FastAPI 契约不依赖模型服务协议。
- 在应用代码中保证输出维度和顺序，不依赖生成式格式。
- 在最多准入 64 个同步请求时约束内存和 GPU 压力，并保证请求间公平。
- 通过类型化、带说明的配置和实测负载方案，使部署与调优可复现。
- 支持使用模拟后端进行本地开发，并使用真实模型进行类生产测试。

**非目标：**

- 训练、微调或量化 Hy-MT2。
- 身份认证、计费、持久化、后台任务或跨主机分布式队列。
- 流式返回部分译文，或从 `/translate` 返回部分成功结果。
- 服务启动时通过不断探测直到 OOM 来自动选择生产 GPU 限制。
- 默认将内部 vLLM API 发布到 Compose 网络之外。

## 设计决策

### API 编排与模型服务分离

FastAPI 和 vLLM 作为两个独立服务运行：

```text
调用方 --> FastAPI /translate --> 有界调度器 --> vLLM /v1/chat/completions
               |                                      |
               +--> 响应组装                          +--> Hy-MT2-1.8B
```

API 镜像由 `docker/Dockerfile.api` 构建。Compose 直接引用 `vllm/vllm-openai:v0.28.0`，只要该镜像保持兼容，就无需 `Dockerfile.vllm`。这样可以避免 API 镜像携带 CUDA 依赖，允许两个服务独立进行就绪检查和重启，也为每个 GPU 运行一个模型副本留出空间。单容器进程管理方案会将模型冷启动与 API 重启耦合，并使健康检查和扩容语义不清，因此不采用。

默认拓扑包含一个 API 进程和一个张量并行度为 1 的 vLLM 实例。单个异步 API 进程足以承载 64 个打开的请求，并保证准入和在途限制在该部署内全局生效。负载测试证明需要跨 GPU 路由时，可通过可选 Compose 覆盖增加模型副本。多个 API 副本需要分别规划容量或使用共享准入层，因此不作为默认配置。

### 使用分层 Python 应用

`src/transflow` 包采用以下职责边界：

```text
src/transflow/
  main.py                 应用工厂与生命周期
  api/                    路由与 HTTP 错误映射
  schemas/                请求和响应模型
  core/                   类型化配置与日志
  domain/                 语言注册表及任务/结果类型
  services/               翻译编排与结果组装
  scheduler/              准入、公平性、取消与限制
  inference/              后端协议与 vLLM HTTP 客户端
  observability/          指标采集
```

推理后端定义为小型异步协议，使单元和集成测试可以使用确定性模拟实现。不在路由中直接调用 `transformers.generate()`，因为这会阻塞请求处理、重复模型生命周期职责，也不具备 vLLM 的连续批处理能力。

### 按索引跟踪每个翻译单元

对于包含 `T` 条文本和 `L` 个目标语言的请求，分配 `L x T` 结果矩阵。所有精确空字符串位置先填入 `""`，其余每个组合均创建一个包含请求 ID、文本索引、目标语言索引、提示词和期限的翻译单元。每个完成结果只能写入自身矩阵坐标，所有必需坐标完成后才返回响应。

调度器按文本位置分片推进，默认分片大小为 60，并交错处理已准入请求，不会一次性启动首个请求的全部 `T x L` 协程。全局在途信号量限制 vLLM 调用，有界准入信号量保护同步 API，物理 GPU 批处理仍由 vLLM 连续批处理负责。不采用分隔符拼接文本，因为生成模型无法保证分隔符数量和位置。

vLLM 客户端还会通过已验证的 `/v1/chat/completions/batch` 端点微批处理独立翻译单元。8 个客户端工作协程分别等待 2 毫秒、每批收集最多 32 个会话，以减少内部 HTTP 和 JSON 开销，同时保留每个翻译单元对应的选择索引。返回选择按 `choice.index` 校验并重排，随后才完成各自的 future。该方式与拼接原文不同：每个会话都有独立聊天模板、生成序列、future 和矩阵坐标。

客户端断开或请求到期时，取消会传递到排队任务，并尽可能使用后端请求标识中止活动的 vLLM 生成。任一单元失败都会使公开请求原子失败。仅重试能够确认发生在推理请求被接受前的故障；不重试超时，避免重复执行仍在运行的高开销任务。

### 由 Hy-MT2 判断各条源语言

将每个受支持的 API 代码映射到目标语言全名，并使用模型文档规定的指令要求仅返回译文。不增加独立源语言检测器，因为短字幕片段经常存在歧义，而 Hy-MT2 可以在没有显式源语言字段时进行多语言翻译。即使非空文本看似已使用目标语言，也始终提交模型处理，以符合约定响应示例。

不发送系统提示词，因为模型文档未作此要求。每次后端调用都显式发送生成控制参数，避免模型镜像中的 `generation_config.json` 静默改变服务行为。初始配置采用确定性生成和有界输出 token；生产前通过质量与负载测试对比厂商推荐的采样参数。

### 启动时只校验一次带说明的 TOML 配置

项目级 `config.toml` 被解析为 `server`、`api`、`scheduler`、`inference`、`generation`、`response`、`logging` 和 `metrics` 的嵌套类型化配置。每个不直观的键旁都有说明用途、单位和调优影响的简短注释。使用 `TRANSFLOW_` 前缀和嵌套分隔符的环境变量可以覆盖 vLLM URL、GPU 选择和日志级别等部署值。

配置在进程生命周期内不可变。无效限制、不安全的参数关系或缺失必需值会在接受流量前导致启动失败。关键关系包括：分片大小不超过请求文本上限、期限为正数、队列容量至少能容纳每个已准入请求的一个分片，以及提示词加输出 token 预算不超过配置的模型长度。不支持动态重载，因为在途请求期间改变准入和生成行为会破坏容量控制与结果可复现性。

### 保持约定的公开响应契约

请求与响应封装使用 Pydantic 模型。默认公开模型标签为 `seaCraft-translation-model`，与内部 vLLM 服务模型名相互独立。请求 ID 使用可配置的 `seaCraft-` 前缀加防碰撞、可排序 token。仅在完整矩阵组装完毕后，使用单调时钟计算 `process_time_ms`，并将 `finished_time` 记为 Unix 秒。

校验错误映射为 422，准入容量耗尽映射为 429，后端未就绪映射为 503，请求期限到期映射为 504。内部异常详情与请求 ID 一并记录，但不会返回调用方。

### 模型产物不进入 Git 和镜像层

使用以下部署结构：

```text
model/Hy-MT2-1.8B/        本地权重，已忽略
docker/Dockerfile.api     仅包含 FastAPI 的镜像
docker/compose.yaml       API 与已验证的 vLLM 镜像
docker/compose.multi-gpu.yaml
```

`.gitignore` 和 `.dockerignore` 均排除模型内容，仅保留小型 README 说明放置方式。模型以 `/model:ro` 挂载到 vLLM。默认只发布 FastAPI，API 通过 Compose 私有网络地址 `http://vllm:8000/v1` 访问 vLLM。根据冒烟测试，vLLM 健康检查至少预留 180 秒冷启动时间。可另行提供只监听本机的调试端口覆盖。

### 正确性测试与硬件容量测试分离

单元测试覆盖校验、语言映射、空位置、矩阵顺序、错误映射、取消和配置。集成测试让 FastAPI 使用模拟后端，以强制产生乱序完成和失败。真实模型冒烟测试验证启动、就绪状态和已知翻译。

独立负载测试工具对分片大小 `8/16/32/60` 和并发量 `1/8/16/32/64` 生成可复现测试方案，覆盖真实字幕长度和配置的最大请求结构。报告记录吞吐量、总延迟与排队延迟的 p50/p95/p99、后端 token 数、GPU 峰值显存、错误/超时/取消数、结果数量错误和 OOM。初始 vLLM 参数保持保守，仅由成功报告更新默认值。测试进程不得与指定 GPU 上的无关任务竞争资源。

### 不记录内容也能观测运行状态

提供 `/health/live`、`/health/ready` 和 `/metrics`。就绪状态取决于配置成功和 vLLM 健康。指标和结构化日志包括请求 ID、文本及语言数量、队列深度、活动单元数、排队时间、后端耗时、总耗时和结果。默认排除原文、译文和完整提示词，减少数据暴露和日志量。

## 风险与权衡

- **最坏情况下，64 个请求、每请求 120 条文本和 6 个语言会扇出为 46,080 个单元**：限制准入和在途任务、公平调度、根据实测方案设置期限，并明确切分只能控制压力，不能减少总计算量。
- **原子响应会在一个单元失败时浪费已完成工作**：保持失败明确且有界；该接口优先保证正确性和可预测结构，不返回部分结果。
- **同步请求可能因长队列保持连接较长时间**：测量最坏耗时、执行期限、暴露队列指标；仅在运行证据确有需要时再考虑异步任务 API。
- **vLLM 或 Transformers 升级可能改变模型行为**：固定已验证镜像版本，在可行时固定摘要，显式发送生成参数，升级前必须通过真实模型回归冒烟测试。
- **已验证镜像会对额外的动态 RoPE 键输出警告**：初期保持已知可用的模型长度，并加入多语言质量检查；警告或输出发生变化时视为升级回归信号。
- **冷启动明显长于权重加载本身**：使用就绪控制和足够的容器健康检查启动宽限期，不立即路由流量。
- **单 API 进程构成单点编排故障域**：初期依赖容器重启策略；仅在确实需要多个 API 副本时引入共享准入。

## 迁移计划

1. 在现有空仓库中创建 Python 包、类型化配置、确定性模拟后端和契约测试。
2. 将 Hy-MT2 文件放置到已忽略的 `model/Hy-MT2-1.8B`，添加 API 镜像和 Compose 部署文件。
3. 在可用 GPU 上启动已验证的 vLLM 镜像，等待就绪，并运行模型冒烟与多语言契约测试。
4. 在无其他负载的 GPU 上运行渐进负载矩阵，保存报告，并根据成功方案设置生产调度、token、超时和显存参数。
5. 使用就绪控制进行部署，在启用全部上游流量前监控队列、延迟、超时和 GPU 指标。

回滚时停止新的 Compose 部署并恢复上游原端点。模型文件保留在镜像层之外，可以独立保留或删除。
